# 物联网领域页面设计指南

> AI 根据 scan 数据的特征，自动识别业务场景，推导出合理的页面设计方案。

## 第一步：识别业务领域

从 scan 数据中的表名、字段名、数据点名称推导业务领域：

| 识别线索 | 推导方向 |
|----------|---------|
| 表名含 meter/energy/power/electric | 能源管理 |
| 表名含 hvac/temperature/humidity/air | 暖通空调 |
| 表名含 camera/video/surveillance | 视频监控 |
| 表名含 parking/vehicle | 停车管理 |
| 表名含 elevator/lift | 电梯管理 |
| 表名含 light/illumination | 照明管理 |
| 表名含 fire/smoke/alarm | 消防安全 |
| 表名含 sensor/environment/pm25/noise/co2 | 环境监测 |
| 表名含 patrol/security/guard | 安防巡更 |
| 表名含 water/pump/pipe/flow | 给排水 |
| 表名含 access/door/entry | 门禁管理 |
| 表名含 production/line/quality/yield | 产线管理 |
| 表名含 soil/moisture/irrigation/crop | 农业种植 |
| 表名含 weather/wind/rain/solar | 气象监测 |
| 表名含 tank/level/pressure/valve | 储罐/管网 |
| 表名含 robot/agv/conveyor | 物流/仓储 |
| tags 含电量/电压/电流/功率 | 用电设备 |
| tags 含温度/湿度 | 温湿度传感 |
| tags 含压力/流量/液位 | 流体系统 |
| tags 含开关/启停/运行状态 | 可控设备 |
| tags 含浓度/PM2.5/CO2/噪声 | 环境质量 |

**识别方法**：统计 scan 数据中表名、字段名、tag 名称中出现的关键词频次，映射到业务域。多个业务域可并存。

## 第二步：设计仪表盘页

每个项目自动生成一个仪表盘（概览页），设计原则：

### 核心统计卡片（所有项目通用）

从 device 表的预设字段推导：

| 统计项 | 数据来源 | 计算方式 |
|--------|---------|---------|
| 设备总数 | 各 device 表 `api.count()` | 求和 |
| 在线设备数 | 各 device 表 `api.count({ online: true })` | 求和 |
| 在线率 | 在线数 / 总数 × 100% | 计算 |
| 报警设备数 | 各 device 表 `api.count({ warnFlag: true })` | 求和 |
| 各子系统状态 | 每个 device 表分别统计在线/离线/报警 | 分布 |

### 趋势图（根据数据点推导）

| 数据点特征 | 推荐图表 | 说明 |
|-----------|---------|------|
| 连续变化量（温度、湿度、功率、流量等） | 折线图 | 24h/7d 趋势 |
| 累计量（电量、水量、运行时长） | 柱状图 | 按日/周/月统计 |
| 状态占比（在线/离线/报警分布） | 堆叠柱状图 | 各子系统对比 |
| 占比分布（设备类型、状态分布） | 饼图/环形图 | 占比分析 |
| 多设备对比 | 多折线图 | 同一维度对比 |

### 仪表盘布局建议

```
┌─────────────────────────────────────────────┐
│ 统计卡片行（设备总数 | 在线率 | 报警数）      │
├──────────────────┬──────────────────────────┤
│ 设备在线分布      │ 设备类型占比              │
│ （堆叠柱状图）    │ （环形图）                │
├──────────────────┴──────────────────────────┤
│ 关键数据点趋势（折线图，选最核心的 2-3 个 tag） │
└─────────────────────────────────────────────┘
```

**选择哪些 tag 上趋势图**：优先选择与项目核心业务最相关的数据点：
- 能源项目：总功率、日用电量
- 暖通项目：送风温度、回风温度
- 环境项目：PM2.5、CO2、温湿度
- 水务项目：管网压力、流量、液位

## 第三步：设计各子系统页面

### 页面结构推导

每个 device 表生成一个列表页，结构如下：

```
┌─ 页面标题 + 描述 ─────────────────────────────┐
├─ 过滤器（自动根据字段推导）                     │
├─ 数据表格                                      │
│  ├── 设备编号                                   │
│  ├── 设备名称                                   │
│  ├── 关键自定义字段（根据业务意义选择）           │
│  ├── 在线状态（预设字段）                        │
│  ├── 报警状态（预设字段）                        │
│  └── 通信时间（预设字段）                        │
└─ 分页器                                        │
```

### 过滤字段选择规则

不是所有字段都适合做过滤器，根据数据特征选择：

| 字段特征 | 是否适合做过滤器 | 示例 |
|----------|----------------|------|
| 枚举/分类型字段（building、area、type、status） | ✅ 适合 | 楼栋、区域、设备类型 |
| 布尔状态字段（online、warnFlag、disable） | ✅ 适合 | 在线状态、报警 |
| 自由文本字段（name、id、remark） | ❌ 不适合 | 设备名称、编号 |
| 数值型字段（温度、功率） | ❌ 不适合 | 需要范围选择，过滤器不支持 |

### 表格列选择规则

| 字段优先级 | 说明 |
|-----------|------|
| **必选** | id、name、online、warnFlag（预设字段） |
| **推荐** | 业务分类字段（building、area、type） |
| **可选** | connectTime、其他自定义字段 |
| **不推荐** | disable（管理属性，非展示关注点）、off（与 online 冗余） |

### 设备表页面的实时数据展示

对于设备表的 tags，判断哪些需要展示在页面上：

| tag 特征 | 是否展示在表格中 | 原因 |
|----------|----------------|------|
| 当前值有业务意义（温度、湿度、功率、压力等） | ✅ 展示 | 用户关注实时值 |
| 累计值（总电量、运行时长） | ✅ 展示 | 用户关注累计数据 |
| 控制相关（开关、设定值） | ❌ 不展示 | 属于控制操作，不是展示 |
| 原始采集值 vs 转换后值 | 用转换后值 | 更直观 |

> 实时数据通过 `useTag` 订阅，在表格列中显示实时值。

## 第四步：设计普通表页面

normal 表根据内容特征决定展示方式：

| 数据特征 | 推荐展示方式 |
|----------|------------|
| 多行结构化记录（巡更记录、维保记录、日志） | 表格 + 过滤器 + 分页 |
| 配置/基础数据（楼宇信息、区域信息） | 表格 + 过滤器 |
| 统计/汇总数据 | 卡片列表 |

## 第五步：推导页面间联动

| 场景 | 联动方式 |
|------|---------|
| 仪表盘统计卡片 → 子系统列表页 | 点击卡片跳转到对应页面 |
| 仪表盘趋势图 → 设备详情 | 点击图表数据点跳转 |
| 设备列表 → 设备详情/实时数据 | 点击行查看详情 |
| 报警统计 → 报警列表 | 点击报警数量跳转报警页 |
| 列表页过滤器 → 数据联动 | 过滤条件同步到数据查询 |

## 设计检查清单

生成报告前，自检以下项：

- [ ] 仪表盘是否有 3-5 个核心统计卡片？
- [ ] 趋势图是否选择了业务最相关的数据点（而非随机选）？
- [ ] 每个页面是否只展示了用户真正关注的字段（而非所有字段）？
- [ ] 过滤器是否选择了分类/枚举型字段（而非自由文本）？
- [ ] 设备表页面是否展示了关键的实时数据点？
- [ ] 页面间是否有合理的跳转/联动关系？
- [ ] 是否有遗漏的重要业务视角（如能耗对比、报警趋势）？
